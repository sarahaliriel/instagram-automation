## Code inventory and boundaries

The schema and ingestion path are evidence of capabilities, not proof that real data is currently being collected. See `prisma/schema.prisma`, `src/modules/webhooks/comment-events.ts`, `src/server/db/ingest-comments.ts`, `src/server/jobs/` and `src/server/delivery/`.

- Incoming webhook bodies can contain account, media, comment, parent and author IDs, username, comment text and notification time. Parsing handles author ID and parent ID in memory; username is validated but not retained in the parsed event. Raw bodies are not persisted by the comment ingestion path. Unsupported messaging events are ignored. A comment can itself contain sensitive information.
- PostgreSQL can store account, media and comment identifiers, encrypted comment text, timestamps, source, receipt, outbox, processing history, leases, retry counts and error codes. Manual GET provenance and provider creation time are represented in the schema. Author ID, username and raw webhook are not stored in the comment table. Identifiers and linked metadata can still be personal data.
- Rules include names, keywords and encrypted message templates; execution records link a comment to a selected rule/keyword and can contain encrypted reply intent. Delivery records contain states, attempt timestamps, limited error/status codes, approval identifiers and encrypted operation identifiers. These may relate to identifiable people. Real messaging is disabled and production paths are blocked.
- Account credentials and encryption keys are configuration secrets, not comment-table fields. Operator-entered rules and credentials may themselves identify a person. Request correspondence, host access logs/IP addresses, job-provider records and backups may contain personal data if those services are used; their actual contents, recipients and retention remain unverified.

## Existing rights and retention mechanisms

`src/server/db/data-rights.ts` prepares a scoped snapshot and performs signed, expiring approval-based child-first deletion for one account/comment **only** when the configured and actual database is the isolated loopback `instagram_rights_test`. It refuses active leases, sending and certain fallback/evidence cases. It removes related attempts, actions, execution, transitions, outbox, receipt and comment, retains shared account/media/rules and a case ID/digest receipt, and has replay and snapshot checks. This is a test-only implementation, not an operational production procedure or complete person-wide erasure. It does not delete Instagram content, external provider data or backups; future re-ingestion and preservation of deduplication evidence require design. No subject-access export, automatic retention purge, public deletion endpoint or validated production rights workflow was identified. Rule draft edits delete replaced keywords and archiving retains rules; these are administration, not rights fulfillment. No backup or subject-access export tool is included in this public copy. Evaluate all copies and provider logs after hosting is selected.

Before publication confirm identity verification and secure intake, search scope, rights-response deadlines under applicable law, access/export and correction handling, exceptions, deletion verification, replay suppression, backups and provider requests. Test with representative scenarios and approve accountable owners; do not claim completion based on the isolated test routine.
