# Deployment plan — proposed, not deployed

The current model is one Instagram account operated by a designated operator and supported by a technical maintainer. The application is not a public SaaS. No provider, region or production activation is approved. Production integration, jobs and delivery are disabled by design; do not bypass their guards.

## Separation

Public visitors → HTTPS static host → audited `legal-site/static-out` (home, privacy, terms, deletion; HTML/CSS). This site needs **no Meta token, PostgreSQL connection or Inngest service**, at build or runtime. `legal-site/scripts/build.mjs` copies an allowlist from `../src/app`, strips scripts and audits the artifact. It rejects environment variable names associated with secrets and site `.env` files; test compatibility with any host's automatically supplied variables. Build from the sanitized copy with access to the parent sources, without backend secrets. A static host may still collect access logs; identify its practices. Vercel configuration is only a candidate, not an established hosting arrangement. Inspect the generated artifact, URLs, HTTPS, accessibility and absence of backend routes before approval.

Separately, a future protected backend would receive Meta HTTPS webhook requests at its dedicated public endpoint, validate the raw-body HMAC and account, and durably commit comment and outbox records in PostgreSQL before acknowledgement. An authenticated job service/worker would dispatch the outbox and process jobs, with retries, leases and fencing. Administrative routes must be protected separately and must not be exposed by the legal site; current Basic authentication is minimal and requires a production security review. Secure operator access, origin controls, secret management, monitoring and incident response need design and verification. No live subscription, hosted processing or delivery is enabled or authorized by this plan.

## Backend prerequisites for a future proposal

- Choose a supported runtime and hosted PostgreSQL provider and region; use TLS with certificate verification, least-privilege separate application and migration credentials, restricted network access, connection pooling compatible with Prisma/transactions, capacity and availability monitoring. Store encryption keys separately in a secret manager with access controls, rotation and recovery plans. Test encrypted backups and restore, define retention and deletion propagation, and explicitly target and review migrations; never run destructive integration tests against hosted data.
- Provision a hosted Inngest-compatible job service and reachable authenticated handler, with signing/event credentials managed separately, scheduled outbox dispatch, durable retries, idempotency, lease expiry/fencing, monitoring and recovery of stuck jobs. Establish provider access, regions, retention and contracts. Existing workers are local/development and production-disabled; hosted readiness is not implemented by this document.
- Select a stable public HTTPS webhook endpoint and domain, configure the Meta app and verification secret, preserve the exact raw request body for HMAC verification, restrict account/event scope and handle retries, duplicates, limits and durable acknowledgements. Confirm current Meta permissions, app review, subscription and platform requirements directly with Meta before any separately authorized activation. Protect dashboard routes independently; callback verification alone does not enable or prove event delivery.
- Assess delivery uncertainty, error handling, rate limits, operational alarms and rollback; live messaging and public fallback require separate explicit approval, implementation review and end-to-end verification.

## Protected draft preview and minimum legal-site release

A preview is a deployment and needs separate authorization. Before creating it, use a dedicated Vercel project and enable Vercel Authentication for preview deployments; verify from an unauthenticated private session that the draft is inaccessible and confirm authorized reviewers can sign in. Do not assume `noindex` restricts access. Do not generate share links or bypass credentials unless expressly needed and authorized. Review plan-specific protection settings before deployment. Vercel documents [Deployment Protection](https://vercel.com/docs/deployment-protection) and [Vercel Authentication](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/vercel-authentication).

The legal project requires no Vercel OIDC backend federation. When federation is enabled, Vercel can inject `VERCEL_OIDC_TOKEN` during builds. The name guard permits only this exact platform variable; the Next.js subprocess receives a minimal environment that excludes it. Other secret-like names remain rejected, including other Vercel secrets. The failed deployment of commit `2826efd` did not report the rejected names, so its exact trigger is unconfirmed; `VERCEL_AUTOMATION_BYPASS_SECRET` is a documented platform variable that would match if present. The guard now reports only rejected names (never values). Review build-log access before using the diagnostic, since names may reveal configuration. In an explicitly authorized protected diagnostic deployment, inspect those names and their origin; remove unnecessary project or team credentials and only consider a narrowly scoped platform exception after verifying its origin and need. Do not use or disclose values. Do not configure backend secrets; confirm the actual build environment and output in the protected preview. The build copies sources outside `legal-site`, so enable access to files outside the Root Directory if that option is available; otherwise configure the repository root as Root Directory and adjust the install, build and output paths accordingly. See [Vercel OIDC](https://vercel.com/docs/oidc) and [system environment variables](https://vercel.com/docs/environment-variables/system-environment-variables).

For a separately published static legal site, the minimum is: validate a working request channel and its operational ownership; approve accurate privacy, terms and deletion instructions including hosting logs and actual providers; settle necessary legal and operational decisions; audit the standalone artifact; select the host/domain and contracts; then verify HTTPS, public access to the approved pages and absence of backend routes. Production dashboard, database, jobs, Meta webhook activation and message delivery are not prerequisites for hosting the static pages. Public accessibility may be required for submission to Meta; assess the current requirements for the exact app and use case before submission.
